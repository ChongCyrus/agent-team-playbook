## 3. 日常实现流水线（S0–S6）

### 3.1 变更与中断（先于流水线生效）

- **需求变更/新增**：不直接插队实现 → 回 S0 评估影响（验收、档位、写范围、依赖），重排任务板；影响大则开新一轮。
- **半成品处理**：标记为「进行中 + 断点备注」，不得混入「完成」。
- **紧急插入**：允许先做最小应急，但必须登记，并在升档后的流程里补齐 S0–S5——**顺序前移不等于流程豁免**；临时补丁不得变永久。
- **目的变更**：以用户最新意图为准，旧任务书作废并记录原因，不留"两套目标"并行。

### 3.2 P0 善后（任何阶段通用）

数据损坏 / 安全 / 全局阻塞 / 已对外发布的问题：

1. 先止损（回退、开关、隔离），**不边查边改**；
2. 记录现场（复现步骤、日志、影响范围）；
3. 修根因，不只修症状（被污染的数据也要修产生逻辑）；
4. 补回归用例；
5. 进复盘，更新检查项。

禁止无记录的「热修」。

### S0 · 目标与验收

- 输入：用户需求 / 反馈 / 上轮结论。
- 产出（**按任务类型区分**）：
  - **功能型**：目的、**可测验收标准**、非目标、约束、已知风险。
  - **修复型**：目的 + **可复现步骤**、现象与边界（何时出现/何时不出现）、影响面初判、当前基线（改前行为），再补验收标准。
- 出口：能一句话说清「做成什么样算完成」，且标准可被验证；修复型还要求**能稳定复现**（复现不了就先在 S1 调查里解决，见下）。
- 坑：需求没读懂就开工；验收标准是「感觉对了」；**修复型没复现就动手改**（等于猜）。

### S1 · 调查与策划（先证据，后方案）

> **为什么有"调查"**：不知道现状与根因就策划，等于在假设上盖楼。修复型尤其如此——**先找根因，再谈怎么修**。

**A. 调查（为策划提供依据；可与 B 交替进行，但进入 S2 前不得有未决调查项）**

| 任务类型 | 调查什么 | 方法 |
|---|---|---|
| **修复型** | 复现 → 定位范围 → 根因假设与验证 | **沿用 S4 的同一套方法**：源码级 + 短测、针对性 + 相关性 + 系统性；工具手段如二分定位、日志/断点、最小实验、对照实验（改前/改后） |
| **功能型** | 现有实现、接口约定、依赖顺序、既有风格与约束 | 读代码与配置、查调用方、确认外部契约；必要时做小实验验证假设 |

**调查的出口**：根因（或对功能型而言的关键事实）有证据支撑，不是"我觉得大概是"。**证据不足不许进 B 定方案**，可先做最小实验。

**调查与审计的方法相同、目的不同**：调查求**根因**，审计求**无遗漏**。所以本条直接复用 S4 的方法，不新增阶段。

**B. 策划（逐层由粗到细，写任务书）**

单 agent 或多 agents 协作，**上一层结论未定，不展开下一层**：

| 层 | 内容 |
|---|---|
| L0 | 目的与验收（为什么做 / 做成什么样） |
| L1 | 总体方案、技术路线、边界与非目标 |
| L2 | 模块划分、接口契约、数据流、依赖顺序 |
| L3 | 可分配的任务与步骤、写范围、验证方式 |
| L4 | 执行细节（动手时才展开，不提前过度细化） |

- 若下层推翻上层（如实现发现接口不可行）：**回到对应层改任务书并同步全员**，禁止边写边改需求。
- **修复型任务的策划要求**：方案必须写明「**根因 → 修改点 → 为什么这个改法能消除根因（而非压症状）→ 同类问题是否一并处理**」。
- 产出：任务书（`04-任务书模板.md`）。出口：没参与策划的人也能独立执行。

### S2 · 评审与打磨（改任务书）

评审四问：**可行性**（路径、成本、依赖成立吗）、**合理性**（拆法最优吗、是否过度/欠缺、边界覆盖吗）、**完整性**（主路径/分支/失败路径/回滚都覆盖了吗？验收标准逐条有对应吗？有没有"以后再补"的洞、漏掉的需求点或影响面）、**优越性**（有更简单/更稳/更快的替代吗）。

四问顺序是递进的：能不能做 → 该这么做吗 → 有没有漏 → 还能更好吗。**完整性这一问专门防"方案看着对、但少了一半"**——这类缺口往往到 S4 审计或 S5 真机才暴露，代价最高。

- 允许红队视角：主动找「这个方案会怎么失败」。
- 产出：修订后的任务书 + 结论（通过 / 有条件通过 / 打回原因）。
- 出口：无未处理分歧；分歧用证据或最小实验裁决，并记录理由。

### S3 · 实现（任务板驱动）

- 建任务板（`05-任务板.md`），按依赖排序，标注写范围。
- 分配：一任务一主责、写范围互斥、接口先定后并行。
- 执行：先领取再动手，小步提交，每步立即做最小验证。
- 出口：条目全部完成且附证据；无跨范围越界改动。

### S4 · 审计（查至无误，但必须有终点）

- 针对性、相关性审计为主，**源码级审计 + 短测**，不做大规模重测。所谓针对性：只审本任务验收标准、改动面、以及改动波及的风险面，**不无限扩大到全库**。
- **全面、系统优先于抽样**：审计目标是"查不出遗漏"，不是"抽查通过"——漏一个 bug 的代价通常是整轮返工，远高于多查十分钟。做法：①按验收标准**逐条**给出检查结果；②按下方清单 12 项维度过一遍；③做**影响传播分析**：改动波及的调用方、依赖方、共享状态、配置、文档是否同步；④关键路径验证正反例（正常 / 异常 / 边界 / 并发 / 取消），不只 happy path。
- **追根因，不只修表象**：修复一处后必须反问「**还有没有同类/相关的隐藏 bug**」——同源代码路径、同类输入、并行分支、异常与并发路径、被静默吞掉的兜底、周边未覆盖的调用方；只让当前症状消失即算未完成，因为隐藏问题会在后续轮次以返工形式出现。
- 交叉审计：写的人不审自己关键改动（条件允许时）；单人或无队友时，改为**隔一次上下文后冷读、对照清单逐条过**（不要在刚写完的兴奋状态里自审）。
- **终止条件（必须满足其一）**：
  1. 验收标准逐条都有检查结果；高风险项（数据/安全/不可逆/并发）零未决；
  2. 连续一次复审无新增高/中等级问题；
  3. 达到开场声明的本轮时间盒（`02-效率与档位详解.md` §2.4 参考值）——未决项必须登记，交 Lead 决定「修/接受风险/延期」，**不允许静默放过**。
- 产出：问题清单（等级/位置/建议修法）→ 修复 → 复审。出口：高等级问题清零，低等级有明确处置。

**问题分级与去向（审计产出必须落表，不许只留在脑子里）**

| 等级 | 判定 | 去向 | 走哪档流程 |
|---|---|---|---|
| **高** | 阻断、数据损坏、安全、需求不满足 | **本轮立即**回 S3 修 → S4 复审 | 继承本轮档位（不低于标准） |
| **中** | 边界缺失、错误处理不足、可维护性差 | 登记为本轮遗留，**下一轮首项** | 按问题性质定档（多为快速/标准） |
| **低** | 风格、命名、可选优化 | 只登记，不阻塞交付 | 快速档，或明确接受风险 |

**回流的三个约束**（防失控）：

1. **深度上限 1 层**：回流任务中再发现的问题只登记，不再触发新一轮回流——否则会无限递归。
2. **时间盒保护**：只有高等级回流本轮；中/低等级一律出轮，避免撑爆开场声明的时间盒。
3. **留痕**：回流必须在任务板建**子条目**（`05-任务板.md`），备注来源审计、原问题等级、父任务；不能只存在于对话里。

**审计清单（按需勾选）**

- [ ] 与验收标准逐条对应，无遗漏、无多做
- [ ] 边界：空值、极值、超时、断网、重复操作、并发、取消
- [ ] 错误处理：失败可见、不静默吞异常、信息可诊断
- [ ] 数据与状态：一致性、持久化、迁移、回滚
- [ ] 资源：句柄/连接/定时器/监听器释放
- [ ] 安全：密钥不入库不入日志、输入校验、权限
- [ ] 代码卫生：无重复实现、无死代码、命名分层一致、无调试残留
- [ ] 兼容性：接口/配置/协议变更向后兼容或有说明
- [ ] 可观测性：关键路径有日志/指标便于定位
- [ ] 测试：关键路径与已修 bug 有回归用例
- [ ] 文档与注释：行为/接口/配置变化已同步更新
- [ ] 性能：关键路径无明显退化（必要时有基线）

### S5 · CI/CD 门禁 与 真机验证（真实体验）

> **为什么"与"不是"→"**：两者**执行可并行、判定是 AND**。写成箭头会让人误以为"必须等 CI 全绿才能碰真机"，白白浪费 CI 的等待时间，也拖晚体验类问题的发现。
> 真正的启动门槛不是"CI 通过"，而是"**有可运行产物**"——构建成功即可并行开始，不必等测试全绿。

**并行规则（本节核心）**

| 项 | 规则 |
|---|---|
| **启动条件** | 构建成功、有可运行产物 → **A 与 B 同时开始**；不要求 A 全绿 |
| **通过条件** | A 全绿 **且** B 通过（**AND，不是先后**）；任一未过，S5 不算完成 |
| **唯一例外** | **构建失败（无产物）** → B 无法启动，此时必须先修构建（这是 A 里唯一会阻塞 B 的红灯） |
| **版本锚定** | B 必须记录验的是**哪个构建号 / commit**；并行期间若 S3 有新改动，最终交付的必须是「A 绿、B 通过」的**同一个版本** |

**并行带来的收益**（为什么值得）：CI 跑批的时间里人已经在机子上走路径；体验类问题（别扭、多余、缺一环）不依赖测试结论，能**更早**回 S3；两头都坏的方案会在更早的时点被同时发现，而不是串行排队各等一轮。

**A. CI/CD 门禁（机器判定，可与 B 并行）**

- 按档位跑对应流水线：**快速**＝构建 + 本改动自测；**标准**＝+ 类型检查 / lint / 全量单测 / 回归用例；**严格**＝+ 集成测试 / 产物校验 / 预发（staging）部署与冒烟。
- 门禁内容：构建成功、静态检查通过、回归无新增失败、产物可部署；有发布动作的走 CD 到预发，**不在本步直发生产**。
- 失败处理：CI 红 → 当作 **实现 bug**，回 S3 修 → S4 复审 → 重跑门禁。**红了不等于要停掉 B**（只在构建失败、无产物时才停）；但**绝不能带着红灯判定通过**。
- 记录：流水线链接 / 构建号 / 结果（作为交付证据的一条，也是 B 的版本锚点）。

**B. 真机验证（真实体验）**

- **真机 = 真实运行环境**：真实设备/浏览器、真实数据、真实网络、真实操作习惯，不只是手机。
- 按用户真实使用路径端到端走一遍，不只看单测绿、也不只看 CI 绿。
- 记录：**验的是哪个构建号** + 通过的路径、偏差、与预期的差距。
- **失败回环**：先定位层级再修——
  - 实现 bug → 回 S3 修 → S4 复审 → S5 重验（**重验必须换新构建号**）；
  - **根因判断错**（S1 调查的假设被证伪）→ 回 S1 重新调查再策划；
  - 策划缺陷（方案/拆法/接口不成立）→ 回 S1-B/S2 改任务书 → 重排任务；
  - 需求理解错 → 回 S0 与用户对齐。
  禁止「哪里坏打哪里」的局部补丁式返工。
- **P0 事件**（数据损坏 / 安全 / 全局阻塞 / 已发布问题）：立即停止验证、按 §3.2 善后，不在验证环节边查边改。
- **出口**：A 全绿 + 核心路径全部走通、体验无明显不合理，**且两者验的是同一版本**。

### S6 · 复盘与固化

- 三问必答：**哪里最慢？哪里最痛？哪条规则该改？**
- 产出（写入 `AGENTS.md` §7 指定的复盘日志）：①问题与根因；②有效做法；③规则/模板/测试的增删改（或「无变更+理由」）；④下轮观察指标。
- **必做落地检查**：本轮每条结论都要回答「**已固化到哪**」——核心条款 / 分册 / 检查项 / 测试 / 脚本 / 经验库（`docs/workflow/practices/`）。答不出来的结论不算闭环，下次必然重踩。
