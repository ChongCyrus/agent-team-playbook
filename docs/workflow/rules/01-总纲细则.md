## 1. 总纲：反馈驱动的自我进化

### 1.1 总纲（全文最高的原则）

> **过程中不断获取反馈，按实际反馈（负面反馈、正向反馈、优化方向）做相应的障碍消除/减弱、调整、优化改进；对象同时包括「项目本身」与「工作流本身」；动作上先策划（怎么消除/减弱，或优化改进方案），再执行。**

总纲服务于两件事，其余都是手段：

1. **目的实现**：做出用户真正需要的东西，且在真实使用场景下站得住。
2. **效率**：用尽可能少的时间与返工，稳定地达到 1（效率 = 稳定性 × 速度；返工是最贵的开销，稳定性是最大的时间杠杆）。

**「目的实现」的七个展开**（缺一即为半成品，后续必然返工）：

- **合理性**：做法要**对得住目的、对得住项目和用户真实体验**——不出现"技术上没错、逻辑上也通，但用起来不合理/不符合直觉/与项目既有设计冲突"的情况。判定视角有两个：①**目的角度**——这个设计真的在服务最初的目的吗，有没有偏离或过度？②**用户真实体验角度**——真实使用者按自然方式操作时，会不会觉得别扭、多余、缺一环？两个角度有冲突时以用户真实体验为先，并把结论写进决策记录。
- **优越性**：相对现有做法/同类方案更好（更稳、更简单、更好用），不是"凑合能跑"；
- **健壮性**：异常输入、边界、并发、重复操作、超时、取消都不崩、不产生脏数据；
- **完整性**：主路径、分支、失败路径、回滚都有交代，不留"以后再补"的洞；
- **必要的完善与防御性**：资源释放、幂等、输入校验、可诊断（日志/错误信息）、可维护（分层、命名、无重复）；
- **用户视角**：站真实使用者角度判断"够不够用、好不好用、会不会困惑"，而不是只对齐需求字面；
- **需求补全**：用户常只给大体需求——缺的部分要主动补全，按最佳实践决策并说明，拿不准的就**问用户**；不允许"没说要就不做"。

总纲不因任务规模而豁免，只调整轻重（快速档也要取反馈、也要先策划）。**所有其它条款都是总纲的执行细则；细则与总纲冲突时，以总纲为准。** 追求稳定性不能膨胀成无限打磨——用「下一个真实反馈点」决定何时停手。

### 1.2 反馈：三类 + 主动探索 + 即时登记

| 类型 | 含义 | 必须做的处理 |
|---|---|---|
| 负面反馈 | 缺陷、bug、返工、阻塞、体验差 | 定根因 → 消除或减弱（不以绕过为终点） |
| 正向反馈 | 有效做法、意外收益、顺手好用的路径 | 提炼成可复用模式并**放大/复用**，不只是记修过的 bug |
| 优化方向 | 不痛但可以更好（来自洞察、对比、推演） | 评估价值与成本 → 进待办或做小实验，不做就当没有 |

**主动探索（每轮至少用一种）**：

- 走真实用户路径复演，把自己当第一次使用的人；
- 与「更优的同类实现 / 上一版 / 设计意图」对比找差距；
- 反向假设：「这个方案会在什么情况下失败？」
- 翻历史复盘与决策记录，找同类问题的重复出现；
- 三问：哪里本可以不发生？哪里用户会困惑？哪里下轮一定还会痛？

**即时登记**：反馈一出现就记一行（格式：`类型 | 触发点 | 现象 | 初判动作`），写进当天文件 `docs/workflow/feedback/<日期>.md`（按人分节，避免互相覆盖），不攒到轮末靠回忆——**没记下来的反馈等于没发生**。轮末按 `07-用户交互与度量.md` §8.2 汇总归类。

**正向反馈要"放大"**：把有效做法写进模板、检查项、测试或脚本，让它下次默认发生；只在这一次用了一次，等于没利用。

### 1.3 动作：三种处理 × 两个对象

| 动作 | 何时用 | 要点 |
|---|---|---|
| 消除 / 减弱 | 障碍、缺陷 | 优先消除；消除不了则减弱影响，并登记残留 |
| 调整 | 方案/范围/节奏/期望与现实不符 | 改策划或验收，而不是硬顶；调整同样要记录并同步 |
| 优化改进 | 有明确更优解 | 先小步实验验证，再放大；不一次铺开 |

| 对象 | 覆盖范围 |
|---|---|
| 项目本身 | 设计/策划/功能/代码/测试/文档/用户体验 |
| 工作流本身 | 分工、沟通、任务板、规则、模板、节奏 |

能同时利两对象的优先处理（例如把踩过的坑写成检查项，既修项目又改流程）。

### 1.4 先策划再执行

任何消除/减弱/调整/优化，都先出方案再动手：

- 方案写清：要解决哪个反馈、怎么做、代价与风险、怎么验证、失败怎么回退；
- 影响小且可逆 → 一句话声明方案即可直接做；
- 影响大或不可逆 → 写进决策记录（`AGENTS.md` §7 产物落点）再执行；
- 禁止：无方案地堆改动、边试边改、用「多改几行」代替想清楚。

### 1.5 进化环（默认循环）

```
观察/采集反馈 → 分类归因 → 排序（影响 × 成本）→ 策划方案 → 小步验证 → 固化（规则/测试/模板）→ 度量
        ↑                                                                                          │
        └──────────────────────────────────────────────────────────────────────────────────────────┘
```

- **小步验证**：一次只改一类东西，用最小验证确认方向，再放大。
- **固化**：验证有效的经验必须落到规则、模板、测试或脚本，否则等于没学到。**按使用频率选落点**：每次都用的进 `AGENTS.md` 核心；特定场景的进本目录分册并登记核心 §8 索引；偶发但复发时救命的进 `docs/workflow/practices/`（写法见其 README）。每条经验须写「已固化到」。
- **可回退**：不确定的改动做成可回退形态（开关、独立提交、备份），验证失败能快速归零。
- **度量**：用 `07-用户交互与度量.md` §8.1 指标看趋势，而不是凭感觉说「变快了」。

### 1.6 反馈来源的五层扫描

| 层级 | 来源 | 典型信号 |
|---|---|---|
| 目的层 | 用户真实体验、真实使用路径、验收标准 | 不好用、慢、看不懂、做多/做少 |
| 策划层 | 宏观设计、模块划分、接口、依赖顺序 | 拆不动、耦合、返工、顺序错 |
| 实现层 | 代码、边界、错误处理、并发、资源、日志 | bug、崩溃、脏数据、静默失败 |
| 过程层 | 工作流本身：等待、对齐、重复劳动、空转 | 卡住、来回问、同题多解 |
| 经验层 | 正面反馈（有效做法）、负面反馈（踩过的坑） | 可复用套路、可复用教训 |

用途：**保证不漏来源**；采集到之后按 §1.2 分类、按 §1.3 定动作。**摘要见 `AGENTS.md` §4（常驻）；本表为完整版。**

### 1.7 障碍：先看见，再处理

**阻塞预警信号**（出现任一即主动排查，不等它爆）：

- 同一任务连续多轮无可见产出；
- 同一错误/失败重复出现 ≥2 次；
- 任务板条目滞留明显超过预估；
- 同一问题被反复向不同人提问；
- 依赖方长时间无响应、接口迟迟未定；
- 验证要靠「再跑一次看看」才能判断。

**处理原则**：

1. **先定性**：阻塞（做不下去）还是摩擦（能做但低效）？
2. **先策划**：按 §1.4 出方案，评估代价与副作用，选**最小充分方案**。
3. **优先消除，其次绕过，最后容忍**：绕过与容忍必须登记，不能假装不存在。
4. **一次只解决一个主因**：多因交织时先处理阻断主路径的那一个。
5. **失败两次即换策略**：同一方案连续两次不成立即停止重试，升级或换路（禁止三连闷头重试）。

### 1.8 规则自身的进化

> **摘要见 `AGENTS.md` §4（常驻）；本节为完整版。**

- 本文件是**活的文档**，但**不为改而改**：有反馈才改；无反馈时在复盘里写明「本轮无规则变更及理由」。
- 改规则必须写清：改了什么、为什么、预期改善哪个指标、如何观察；记入 `09-环境适配与变更记录.md` 的变更记录。
- 规则改动同样走小步验证：先用一轮，有效再固化，无效即回退。
- **分节预算**：任一小节超过 12 条时，先合并/删除再新增；重复或失效的条款直接删。
- **偏离流程的通用纪律**：任何偏离本文件的决定，必须显式声明「为什么 + 已知风险 + 如何回补」；无声明即违规。**规则可以破，但不能悄悄破。**
- **规则冲突时的优先级**：效力条款（目的实现 / 用户真实体验）> 安全与不可逆 > 效率 > 流程形式。冲突按此判定，并把判定写进复盘。
