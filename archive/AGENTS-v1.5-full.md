# AGENTS.md — 多智能体协作开发工作流规则

> **定位**：团队（Lead + 队友）共享的最高工作约定。
> **核心命题（总纲）**：过程中不断获取反馈 → 按「负面 / 正向 / 优化方向」分类 → **先策划**（消除/减弱障碍，或优化改进方案）→ 再执行 → 固化。对象同时包括**项目本身**与**工作流本身**；目标是让「目的实现」与「效率（稳定性 + 时间）」每轮可验证地提升。详见 §1。
> **效力**：与具体任务冲突时，以「目的实现 + 用户真实体验」为准，并把修正写回本文件。
> **它不是装饰**：每条规则必须可执行、可检查；不可执行或无效果的一律删除。**总量受控：单个小节不超过 12 条文字条款（表格/清单另计），超了先合并或删除再新增。**

## 0. 三分钟版

### 0.1 五条铁律

> **总纲优先**：本文件所有条款都是 §1 总纲的执行细则；细则与总纲冲突时，以总纲为准。

1. **先定「做成什么样算完成」再动手**——验收标准必须可判真假。
2. **按风险选流程档位**——不搞一刀切，也不随意裁剪；裁剪必须声明并设定升档条件（§2.4）。
3. **先策划再执行**——动手前先问：有没有更短的路径？
4. **完成 = 实现 + 自检 + 证据**——无证据不算完成。
5. **每轮复盘三问**——哪里最慢？哪里最痛？哪条规则该改？

### 0.2 一轮的定义

一轮 = 一个用户目标/需求从接受到**验证通过**的完整闭环。大目标拆成多轮，每轮必须有独立可验证的产出；跨轮的结论以文件为准，不靠对话记忆。

### 0.3 开场协议（Lead 每轮必做）

**标准/严格档（3 行）**：

1. **目标与验收**：一句话目标 + 可测验收标准。
2. **档位与时间盒**：快速/标准/严格 + 理由 + 本轮时间盒上限。
3. **分工与写范围**：谁做什么、哪些并行、依赖谁。

**快速档可压成 1 行**：`目标 + 验收 = X；按快速档做，不改接口`。收尾同样 1 行。**不要为小改造成流程税。**

### 0.4 收尾协议（Lead 每轮必做）

**结果**（达成/未达成）｜**目的达成自评**（用户最初的目的达到了吗？还是只满足了验收清单）｜**证据**（测试与验证记录）｜**遗留与下一步**（含未决风险）。

### 0.5 阅读指南（别每轮读全文）

**任何角色先读 §1.1–§1.3（总纲、反馈三类、动作与对象）**，其余按「档位 × 角色」取最小集：

- **快速档**：§1 + §2.4 + §10（Lead 另加 §2.5）。
- **标准档 · 队友**：§0–§5 + §6.2 / 6.4 / 6.5 / 6.6 + §9 / §10。
- **标准档 · Lead**：§0–§5 + §2.5 + §6.1 / 6.3 + §9 / §10。
- **严格档**：全文 + 附 A（任何角色）。

规则全文是"需要时查"的，不必无差别塞进上下文（§6.6）。

## 1. 总纲：反馈驱动的自我进化

### 1.1 总纲（全文最高的原则）

> **过程中不断获取反馈，按实际反馈（负面反馈、正向反馈、优化方向）做相应的障碍消除/减弱、调整、优化改进；对象同时包括「项目本身」与「工作流本身」；动作上先策划（怎么消除/减弱，或优化改进方案），再执行。**

总纲服务于两件事，其余都是手段：

1. **目的实现**：做出用户真正需要的东西，且在真实使用场景下站得住。
2. **效率**：用尽可能少的时间与返工，稳定地达到 1（效率 = 稳定性 × 速度；返工是最贵的开销，稳定性是最大的时间杠杆）。

总纲不因任务规模而豁免，只调整轻重（快速档也要取反馈、也要先策划）。**所有其它条款都是总纲的执行细则；细则与总纲冲突时，以总纲为准。** 追求稳定性不能膨胀成无限打磨——用「下一个真实反馈点」决定何时停手。

### 1.2 反馈：三类 + 主动探索 + 即时登记

| 类型 | 含义 | 必须做的处理 |
|---|---|---|
| 负面反馈 | 缺陷、bug、返工、阻塞、体验差 | 定根因 → 消除或减弱（不以绕过为终点） |
| 正向反馈 | 有效做法、意外收益、顺手好用的路径 | 提炼成可复用模式并**放大/复用**，不只是记修过的 bug |
| 优化方向 | 不痛但可以更好（来自洞察、对比、推演） | 评估价值与成本 → 进待办或做小实验，不做就当没有 |

**主动探索（每轮至少用一种）**：

- 走真实用户路径复演，把自己当第一次使用的人；
- 与「更优的同类实现 / 上一版 / 设计意图」对比找差距；
- 反向假设：「这个方案会在什么情况下失败？」
- 翻历史复盘与决策记录，找同类问题的重复出现；
- 三问：哪里本可以不发生？哪里用户会困惑？哪里下轮一定还会痛？

**即时登记**：反馈一出现就记一行（格式：`类型 | 触发点 | 现象 | 初判动作`），写进当天文件 `docs/workflow/feedback/<日期>.md`（按人分节，避免互相覆盖），不攒到轮末靠回忆——**没记下来的反馈等于没发生**。轮末按 §8.2 汇总归类。

**正向反馈要"放大"**：把有效做法写进模板、检查项、测试或脚本，让它下次默认发生；只在这一次用了一次，等于没利用。

### 1.3 动作：三种处理 × 两个对象

| 动作 | 何时用 | 要点 |
|---|---|---|
| 消除 / 减弱 | 障碍、缺陷 | 优先消除；消除不了则减弱影响，并登记残留 |
| 调整 | 方案/范围/节奏/期望与现实不符 | 改策划或验收，而不是硬顶；调整同样要记录并同步 |
| 优化改进 | 有明确更优解 | 先小步实验验证，再放大；不一次铺开 |

| 对象 | 覆盖范围 |
|---|---|
| 项目本身 | 设计/策划/功能/代码/测试/文档/用户体验 |
| 工作流本身 | 分工、沟通、任务板、规则、模板、节奏 |

能同时利两对象的优先处理（例如把踩过的坑写成检查项，既修项目又改流程）。

### 1.4 先策划再执行

任何消除/减弱/调整/优化，都先出方案再动手：

- 方案写清：要解决哪个反馈、怎么做、代价与风险、怎么验证、失败怎么回退；
- 影响小且可逆 → 一句话声明方案即可直接做；
- 影响大或不可逆 → 写进决策记录（附 A）再执行；
- 禁止：无方案地堆改动、边试边改、用「多改几行」代替想清楚。

### 1.5 进化环（默认循环）

```
观察/采集反馈 → 分类归因 → 排序（影响 × 成本）→ 策划方案 → 小步验证 → 固化（规则/测试/模板）→ 度量
        ↑                                                                                          │
        └──────────────────────────────────────────────────────────────────────────────────────────┘
```

- **小步验证**：一次只改一类东西，用最小验证确认方向，再放大。
- **固化**：验证有效的经验必须落到规则、模板、测试或脚本，否则等于没学到。
- **可回退**：不确定的改动做成可回退形态（开关、独立提交、备份），验证失败能快速归零。
- **度量**：用 §8.1 指标看趋势，而不是凭感觉说「变快了」。

### 1.6 反馈来源的五层扫描

| 层级 | 来源 | 典型信号 |
|---|---|---|
| 目的层 | 用户真实体验、真实使用路径、验收标准 | 不好用、慢、看不懂、做多/做少 |
| 策划层 | 宏观设计、模块划分、接口、依赖顺序 | 拆不动、耦合、返工、顺序错 |
| 实现层 | 代码、边界、错误处理、并发、资源、日志 | bug、崩溃、脏数据、静默失败 |
| 过程层 | 工作流本身：等待、对齐、重复劳动、空转 | 卡住、来回问、同题多解 |
| 经验层 | 正面反馈（有效做法）、负面反馈（踩过的坑） | 可复用套路、可复用教训 |

用途：**保证不漏来源**；采集到之后按 §1.2 分类、按 §1.3 定动作。

### 1.7 障碍：先看见，再处理

**阻塞预警信号**（出现任一即主动排查，不等它爆）：

- 同一任务连续多轮无可见产出；
- 同一错误/失败重复出现 ≥2 次；
- 任务板条目滞留明显超过预估；
- 同一问题被反复向不同人提问；
- 依赖方长时间无响应、接口迟迟未定；
- 验证要靠「再跑一次看看」才能判断。

**处理原则**：

1. **先定性**：阻塞（做不下去）还是摩擦（能做但低效）？
2. **先策划**：按 §1.4 出方案，评估代价与副作用，选**最小充分方案**。
3. **优先消除，其次绕过，最后容忍**：绕过与容忍必须登记，不能假装不存在。
4. **一次只解决一个主因**：多因交织时先处理阻断主路径的那一个。
5. **失败两次即换策略**：同一方案连续两次不成立即停止重试，升级或换路（禁止三连闷头重试）。

### 1.8 规则自身的进化

- 本文件是**活的文档**，但**不为改而改**：有反馈才改；无反馈时在复盘里写明「本轮无规则变更及理由」。
- 改规则必须写清：改了什么、为什么、预期改善哪个指标、如何观察；记入附 C。
- 规则改动同样走小步验证：先用一轮，有效再固化，无效即回退。
- **分节预算**：任一小节超过 12 条时，先合并/删除再新增；重复或失效的条款直接删。
- **偏离流程的通用纪律**：任何偏离本文件的决定，必须显式声明「为什么 + 已知风险 + 如何回补」；无声明即违规。**规则可以破，但不能悄悄破。**
- **规则冲突时的优先级**：效力条款（目的实现 / 用户真实体验）> 安全与不可逆 > 效率 > 流程形式。冲突按此判定，并把判定写进复盘。

## 2. 效率的两条腿

### 2.1 稳定性（质量底线）

- **健壮性**：异常输入、空值、超时、断网、并发、重复操作、中途取消都不崩、不脏数据。
- **无屎山**：分层清晰、职责单一、无重复实现、无死代码、命名达意、依赖可控；**遵循项目既有约定，不引入第二套风格**。
- **无 bug**：主路径与关键边界有测试或可复现验证，同类缺陷不重复出现。
- **可回归**：改动能被验证、问题能被复现、回退有路径。

### 2.2 时间账目

| 时间类型 | 说明 | 优化手段 |
|---|---|---|
| 动手 | 编码/写作 | 复用、模板化、减少无谓打磨 |
| 等待 | 等依赖、等审核、等回答 | 并行拆分、提前抛阻塞、预置桩/占位 |
| 返工 | 做错、做偏、做多 | 前置验收定义、先审策划、小步验证 |
| 对齐 | 沟通、解释、来回确认 | 任务书写清、消息自包含、批量沟通 |
| 切换 | 频繁换任务、换上下文 | 按依赖成组执行、减少打断 |

**优化优先级**：先砍返工与等待（收益最大），再压动手时间（收益最小、最易反噬稳定性）。

**成本同看**：上下文长度、模型调用次数、并发成员数也是资源——不是免费的，按需使用。

### 2.3 最优方案与决策记录

- **决策点前至少比较两条路径**（已有实现 / 已有工具 / 换拆法 / 最小闭环），选达成目的程度、成本、风险三者最优者；只有一条路时说明为何。
- 影响面较大或不可逆的决策，**把选择与理由写进决策记录**（附 A），便于复盘与交接。
- 不为「完美方案」拖延：先做可验证的最小闭环，美化留到有反馈之后。
- 不为「快」牺牲不可逆的东西：数据、对外契约、安全、用户可见行为，先稳后快。
- **被否决的方案要留一行理由**（进决策记录），避免下轮重复提议同一个被否方案。

### 2.4 流程分档（避免一刀切与随意裁剪）

| 档位 | 适用 | 必做 | 可简化 | 审计强度 | 验证 | 时间盒（参考） |
|---|---|---|---|---|---|---|
| **快速** | 单点改动、文案/配置、可逆、不动接口 | S0 一句话验收 + S3 + 自测 | 任务书压成 3 行；S2 免；S6 压成 1 行 | 自审：对照验收 + 扫边界 | 最小复现路径 | 15–30 分钟 |
| **标准** | 常规功能与修复，多文件但接口不变 | S0–S6 | S2 改为自审；S6 可 3 行 | 源码级 + 短测；有队友时交叉 | 真实路径走通 | 半天 |
| **严格** | 数据、支付、安全、不可逆、对外契约、大重构 | 全流程 + 红队 + 双重审计 | 无 | 全清单 + 交叉 + 复审 | 真实路径 + 异常路径 + 回退演练 | 1–2 天 |

时间盒仅为参考值，**实际以开场协议声明为准**；不确定时按风险判档，不按"想快点"判档。严格档常跨多轮，时间盒按**单个子任务**计，不是整个项目。

**升档触发（出现任一，立即升档并重排任务）**：

- 涉及数据迁移/删除、支付、权限、密钥；
- 改动对外接口、契约、配置格式；
- 触及多人共享文件（配置、锁文件、统一入口）；
- 同一处两次修不好或原因不明；
- 新增第三方依赖；
- 真机验证失败且无法定位原因。

**裁剪纪律**：简化必须声明「本轮按 X 档执行，理由：…；已知风险：…；出现上述任一触发立即升档」。

### 2.5 优先级与取舍

多任务并存时的排序依据（自上而下）：

1. 用户明确指定的优先级；
2. 解除他人阻塞（被下游等待的任务）；
3. 关键路径上的任务；
4. 价值 ÷ 成本（含风险）更优的任务；
5. 顺手可清的快速清理（≤15 分钟；限于**写范围内、无行为变化**的纯本地改动，越界需 Lead 确认）。

**取舍规则**：每个成员同一时刻只推进一条主线；全局并行主线数由 Lead 控制（建议 ≤3）——**并行是为了压缩关键路径，不是为了显得快**。被打断时记录断点（做到哪、下一步、未验证的假设），避免回来重新推理。

## 3. 日常实现流水线（S0–S6）

### 3.1 变更与中断（先于流水线生效）

- **需求变更/新增**：不直接插队实现 → 回 S0 评估影响（验收、档位、写范围、依赖），重排任务板；影响大则开新一轮。
- **半成品处理**：标记为「进行中 + 断点备注」，不得混入「完成」。
- **紧急插入**：允许先做最小应急，但必须登记，并在升档后的流程里补齐 S0–S5——**顺序前移不等于流程豁免**；临时补丁不得变永久。
- **目的变更**：以用户最新意图为准，旧任务书作废并记录原因，不留"两套目标"并行。

### 3.2 P0 善后（任何阶段通用）

数据损坏 / 安全 / 全局阻塞 / 已对外发布的问题：

1. 先止损（回退、开关、隔离），**不边查边改**；
2. 记录现场（复现步骤、日志、影响范围）；
3. 修根因，不只修症状（被污染的数据也要修产生逻辑）；
4. 补回归用例；
5. 进复盘，更新检查项。

禁止无记录的「热修」。

### S0 · 目标与验收

- 输入：用户需求 / 反馈 / 上轮结论。
- 产出：**目的、可测验收标准、非目标、约束、已知风险**。
- 出口：能一句话说清「做成什么样算完成」，且标准可被验证。
- 坑：需求没读懂就开工；验收标准是「感觉对了」。

### S1 · 策划（逐层由粗到细，写任务书）

单 agent 或多 agents 协作，**上一层结论未定，不展开下一层**：

| 层 | 内容 |
|---|---|
| L0 | 目的与验收（为什么做 / 做成什么样） |
| L1 | 总体方案、技术路线、边界与非目标 |
| L2 | 模块划分、接口契约、数据流、依赖顺序 |
| L3 | 可分配的任务与步骤、写范围、验证方式 |
| L4 | 执行细节（动手时才展开，不提前过度细化） |

- 若下层推翻上层（如实现发现接口不可行）：**回到对应层改任务书并同步全员**，禁止边写边改需求。
- 产出：任务书（§4）。出口：没参与策划的人也能独立执行。

### S2 · 评审与打磨（改任务书）

评审三问：**可行性**（路径、成本、依赖成立吗）、**合理性**（拆法最优吗、是否过度/欠缺、边界覆盖吗）、**优越性**（有更简单/更稳/更快的替代吗）。

- 允许红队视角：主动找「这个方案会怎么失败」。
- 产出：修订后的任务书 + 结论（通过 / 有条件通过 / 打回原因）。
- 出口：无未处理分歧；分歧用证据或最小实验裁决，并记录理由。

### S3 · 实现（任务板驱动）

- 建任务板（§5），按依赖排序，标注写范围。
- 分配：一任务一主责、写范围互斥、接口先定后并行。
- 执行：先领取再动手，小步提交，每步立即做最小验证。
- 出口：条目全部完成且附证据；无跨范围越界改动。

### S4 · 审计（查至无误，但必须有终点）

- 针对性、相关性审计为主，**源码级审计 + 短测**，不做大规模重测。所谓针对性：只审本任务验收标准、改动面、以及改动波及的风险面，**不无限扩大到全库**。
- 交叉审计：写的人不审自己关键改动（条件允许时）；单人或无队友时，改为**隔一次上下文后冷读、对照清单逐条过**（不要在刚写完的兴奋状态里自审）。
- **终止条件（必须满足其一）**：
  1. 验收标准逐条都有检查结果；高风险项（数据/安全/不可逆/并发）零未决；
  2. 连续一次复审无新增高/中等级问题；
  3. 达到开场声明的本轮时间盒（§2.4 参考值）——未决项必须登记，交 Lead 决定「修/接受风险/延期」，**不允许静默放过**。
- 产出：问题清单（等级/位置/建议修法）→ 修复 → 复审。出口：高等级问题清零，低等级有明确处置。

**审计清单（按需勾选）**

- [ ] 与验收标准逐条对应，无遗漏、无多做
- [ ] 边界：空值、极值、超时、断网、重复操作、并发、取消
- [ ] 错误处理：失败可见、不静默吞异常、信息可诊断
- [ ] 数据与状态：一致性、持久化、迁移、回滚
- [ ] 资源：句柄/连接/定时器/监听器释放
- [ ] 安全：密钥不入库不入日志、输入校验、权限
- [ ] 代码卫生：无重复实现、无死代码、命名分层一致、无调试残留
- [ ] 兼容性：接口/配置/协议变更向后兼容或有说明
- [ ] 可观测性：关键路径有日志/指标便于定位
- [ ] 测试：关键路径与已修 bug 有回归用例
- [ ] 文档与注释：行为/接口/配置变化已同步更新
- [ ] 性能：关键路径无明显退化（必要时有基线）

### S5 · 真机验证（真实体验）

- **真机 = 真实运行环境**：真实设备/浏览器、真实数据、真实网络、真实操作习惯，不只是手机。
- 按用户真实使用路径端到端走一遍，不只看单测绿。
- 记录：通过的路径、偏差、与预期的差距。
- **失败回环**：先定位层级再修——
  - 实现 bug → 回 S3 修 → S4 复审 → S5 重验；
  - 策划缺陷 → 回 S1/S2 改任务书 → 重排任务；
  - 需求理解错 → 回 S0 与用户对齐。
  禁止「哪里坏打哪里」的局部补丁式返工。
- **P0 事件**（数据损坏 / 安全 / 全局阻塞 / 已发布问题）：立即停止验证、按 §3.2 善后，不在验证环节边查边改。
- 出口：核心路径全部走通，体验层面无明显不合理。

### S6 · 复盘与固化

- 三问必答：**哪里最慢？哪里最痛？哪条规则该改？**
- 产出（写入附 A 的复盘日志）：①问题与根因；②有效做法；③规则/模板/测试的增删改（或「无变更+理由」）；④下轮观察指标。

## 4. 任务书模板

```markdown
# 任务：<一句话标题>

## 目的
<为什么做，解决什么问题，对应哪个用户反馈>

## 验收标准（可测）
- [ ] ...
- [ ] ...

## 非目标
- 本次明确不做：...

## 约束与假设
- 技术/时间/兼容性/环境约束：...
- 关键假设（不成立需回头改哪一层）：...

## 方案要点
- 总体方案：...
- 模块与接口：...
- 实现步骤（L3）：1) ... 2) ... 3) ...

## 影响面与风险
- 触及文件/模块（= 写范围）：...
- 风险与缓解：...

## 验证方式
- 审计要点：...
- 短测/回归用例：...
- 真机路径：...

## 回退方案
- 失败时如何归零：...
```

**要求**：验收标准可判真假；步骤可独立分配；风险必须有缓解动作；写范围必须具体到文件/目录。

---

## 5. 任务板规范

| 字段 | 要求 |
|---|---|
| ID / 标题 | 稳定、唯一、一眼看懂 |
| 目的 | 对应哪条验收标准 |
| 写范围 | 具体文件/目录，互斥；跨范围必须显式协调 |
| 依赖 | 明确 blocked by 谁；无依赖才可并行 |
| 主责 | 一任务一主责，避免共同负责 |
| 状态 | 待办 / 进行中（附断点备注）/ 阻塞 / 待审 / 完成 |
| 证据 | 测试结果、日志、截图、diff 要点 |

**纪律**
1. 先领取再动手，避免重复劳动。
2. 阻塞时更新状态并写清：阻塞点、已尝试方案、需要的决策/资源。
3. **完成 = 实现 + 自检 + 证据**，缺一不得置为完成。
4. 依赖变化立即同步，避免下游按旧前提施工。
5. 任务板是**唯一进度事实源**，口头进度都要落回板上。
6. 若任务板是共享单文件，由 Lead 独占写、队友提交变更请求——单文件多写是并发覆盖热点。

## 6. 多智能体协作规则

### 6.1 组队判据（先决定单干还是组队）

| 用单 agent | 用多 agent |
|---|---|
| 单一改动面、一次自检可完成、协调成本 > 收益 | ≥2 个互不依赖的改动面 |
| 上下文可一次装下 | 需要「实现者/审计者」分离才可靠 |
| 接口尚未定型（先一个人定下来） | 信息搜集与实现可并行 |
| 探索性、方向不明（先探路） | 存在明确关键路径，加人能压缩它 |

**铁律**：成员不是越多越好。每增加一个成员，必须至少压缩一个真实的等待或返工点，否则不组队。

### 6.2 全体成员共同约定

- **单一事实源**：以工作区文件与实际运行结果为准；不臆测他人产出，不基于传闻决策。
- **先读后写**：改文件前先读当前内容；冲突（版本过期/被他人改动）时先重读、再重排自己的改动，绝不强推覆盖。
- **写范围纪律**：只动自己范围内的文件；必须越界时先申请并同步影响。
- **不重复劳动**：动手前确认没人正在做同一件事；有重叠先协商拆分。
- **证据说话**：结论附证据（测试、日志、复现步骤、diff）；「我试过了」不算证据。
- **不空转**：等待期间做无冲突的准备工作（读上下文、写测试、备验证数据、预置桩），而不是反复询问。
- **失败即报**：同一问题两次尝试不成立即升级，不隐瞒、不硬扛、不换法重试掩盖。
- **消息自包含**：对方无需追问背景即可执行；批量聚合问题，减少碎片化打断。
- **可逆优先**：不可逆操作（删除、覆盖、发布、改数据）先确认；能备份就备份。

### 6.3 Lead 职责

**核心是「让团队跑得顺」，不是「自己写得最多」。**

1. **翻译目标**：把用户意图翻译成可测验收标准与任务书，明确非目标。
2. **决定档位与组队**：选流程档位、时间盒与团队规模，并按变化的风险升/降档。
3. **评审把关**：审可行性/合理性/优越性；对分歧做裁决并记录理由。
4. **安排节奏**：按 §2.5 排优先级与依赖，压关键路径；控制并行度不超过协调能力。
5. **扫阻塞**：按 §1.7 的预警信号主动巡检，第一时间给决策或换路。
6. **守质量门**：审计不省略；合并前审 diff、跑关键测试、确认无越界改动。
7. **保留带宽**：优先做只有 Lead 能做的事（定目标、裁决、终审、对外沟通）；**关键路径缺人时也要下场攻坚**，但不能两手都抓成瓶颈。
8. **做复盘与进化**：更新任务书模板与本文规则，把有效做法固化成流程。
9. **信息不藏**：关键决策、约束变化、验收变化立刻同步全员。

**Lead 自检（每轮）**
- [ ] 每个人的任务都清楚到「不用再问」吗？
- [ ] 关键路径上有人在并行推进吗？
- [ ] 有任务滞留超预期而我没发现吗？
- [ ] 我这轮做的事，有哪件本可交出去？
- [ ] 有未记录的决策或未固化的经验吗？

### 6.4 队友职责

1. **开工确认**：**标准/严格档**或陌生任务，用 1–3 句复述理解 + 计划 + 验证方式；任务书有漏洞立即提出。**快速档不必走形式**，直接干。
2. **按时交付**：按写范围和验收标准执行，小步推进，每步可验证。
3. **自主但不越界**：可逆小决策自己拍；接口变更、跨范围、不可逆操作、需求理解偏差，必须同步。
4. **自检后交付**：对照验收标准自查，跑最小验证。
5. **交付格式**：
   ```
   完成：<任务>
   改动：<文件 + 行为变化>
   证据：<测试/日志/复现步骤>
   风险/未覆盖：<如实说明>
   建议下一步：<可选>
   ```
6. **阻塞处理**：先自解（查上下文/最小实验）→ 两次不成立即上报，附阻塞点与需要的决策。
7. **不扩范围**：顺手发现的问题记录上报，不擅自改；范围变更走 Lead 确认。（§2.5 允许的 ≤15 分钟写范围内纯本地清理除外。）
8. **反馈工作流本身**：流程哪里低效、哪里重复、哪条规则不好用，主动提——这是效率提升的主要来源之一。

### 6.5 沟通协议

- **四要素**：目的 / 现状 / 请求 / 期望答复形式。
- **决策权**：可逆小事自决；跨范围、接口变更、不可逆操作、验收标准变更 → 必须同步或裁决。
- **异步优先**：发出消息后继续推进不受阻的工作，不为等待而停下（除非确实被阻塞）。
- **阻塞分级**：
  - P0：目标不可达、数据损坏、安全风险、全员被堵 → 立即升级，按 §3.2 善后。
  - P1：当天进度受影响 → 立即上报，当天给方案。
  - P2：可绕过 → 登记，不打断主线。
- **禁止**：无信息量的「在吗/怎么样了」；同一条消息反复催；绕过任务板私下改需求。

### 6.6 上下文、信息与成本

- **结论写进文件，不靠对话记忆传递**：任务书、审计结论、决策记录、复盘日志都是载体。
- 队友**不必读全库**：读任务书 + 相关文件 + 接口约定即可开工；需要更深信息时再做针对性检索。
- 大文件分片读、按需检索，避免把整个仓库塞进上下文（时间与成本双杀）。
- **规则也按档位加载**（§0.5），不必每轮读全文。
- **接手三件套**：中途接手或新成员加入，先读「任务书 + 任务板当前状态 + 最近一次复盘/决策记录」，再动手。
- 跨会话/跨轮交接以文件为准；「上一轮说过」不算约定。

### 6.7 共享资源与依赖

- **依赖变更集中申报**：新增第三方库/工具/配置项先报 Lead，避免多人各装一套造成冲突与环境漂移。
- 共享文件（配置、锁文件、统一入口）视为高冲突区：由一人主笔，其余人提交需求。
- 共享环境（测试库、端口、服务）使用前确认占用，用完释放。

### 6.8 并行与串行

- **并行**：写范围互斥、依赖独立、接口已定。
- **串行**：接口未定、共享文件、上游结论会改变下游方案。
- **判断标准**：并行是否压缩了关键路径；只增加协调成本不压缩关键路径的并行应取消。

## 7. 用户交互最小必要原则

- **必须问**：缺失信息会导致不可逆后果或方向性偏差；或用户意图有 ≥2 种合理解释且成本差异很大。
- **不必问**：可从现有代码、文档、惯例合理推断 → 按最合理默认推进，交付时声明「已按…处理，如需调整告诉我」。
- **批量问**：一次列清所有问题，不挤牙膏式追问。
- **问要带方案**：给出选项与推荐项，降低用户决策成本。
- **否决留痕**：用户或 Lead 明确否决过的方向，记录理由，不再重复提议（除非有新证据）。

## 8. 度量与自我进化

### 8.1 观察指标（只做同类任务间的趋势比较，不做绝对值考核）

- **步骤数/工具调用数**（周期时间的代理指标，同类任务纵比；不跨任务类型比较）。
- 返工率（完成后又需修改的比例）。
- 审计漏出率（审计通过后仍被真机/用户发现的问题数）。
- 阻塞次数与滞留时长。
- 沟通轮次（达成一致所需消息数）。
- 重复问题数（同类问题再现 = 没固化）。

指标记入复盘日志，跨轮对比趋势即可；**没有可比数据时宁可空着，也不编造数字**。

### 8.2 每轮复盘（必做，短则三行）

复盘前先把本轮登记的反馈按 §1.2 归到三类（负面 / 正向 / 优化方向），未登记的不算采集过。然后三问：

1. 本轮最大的时间浪费点是什么？根因？
2. 哪条规则/模板/测试应该新增、修改或删除？（无则写理由）
3. 下轮用什么指标验证改动有效？

### 8.3 进化纪律

- **一次只改一个变量**，避免流程与实现同时改导致无法归因。
- **改规则要有证据**：有效保留，无效回退，不留「看起来正确」的装饰性规则。
- **跨轮沉淀**：踩过的坑写成检查项或测试用例；有效的协作方式写成条款。
- **定期清理**：规则、模板、文档同样反屎山，过期即删。

## 9. 反模式清单（禁止）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 无验收标准就开工 | 做偏、返工 | 先 S0，写清可测验收 |
| 小任务上全套流程（流程税） | 拖慢、形式主义 | 按 §2.4 选档并声明 |
| 无声明地偏离流程 | 规则形同虚设 | 声明理由 + 风险 + 回补 |
| 审计无限打磨 / 走过场 | 一边拖死、一边漏出 | 遵守 S4 终止条件与强度分级 |
| Lead 包办所有实现 | 成为瓶颈 | 拆分委派，Lead 守质量门与节奏 |
| 多 agent 抢同一文件 | 覆盖、冲突、重复劳动 | 写范围互斥，先申报后动 |
| 完成不附证据 | 假完成，后期爆雷 | 完成 = 实现 + 自检 + 证据 |
| 同一方案连试三次 | 时间黑洞 | 两次失败即换策略或升级 |
| 把「能跑」当「完成」 | 体验差、隐性债 | 真机按真实路径验证 |
| 需求变更直接插队实现 | 半成品叠加、反复返工 | 回 S0 评估影响并重排任务 |
| P0 问题无记录热修 | 复发、无法归因 | 止损 → 记录 → 修根因 → 补用例 |
| 过度设计/无限打磨 | 拖延、反馈滞后 | 先最小闭环，有反馈再优化 |
| 静默失败、吞异常 | 问题晚发现、难定位 | 失败可见、可诊断 |
| 擅自扩大范围 | 拖慢主线、引入风险 | 记录上报，走确认 |
| 绕过任务板沟通 | 事实源分裂 | 进度一律落回任务板 |
| 为改规则而改规则 | 规则膨胀失效 | 有反馈才改，无则写明理由 |
| 用对话记忆传结论 | 跨轮丢失、重复劳动 | 信息外置到文件（§6.6） |
| 每轮重读规则全文 | 上下文浪费 | 按档位加载（§0.5） |
| 频繁追问用户或闷头乱猜 | 拖慢或做偏 | 按 §7 决策：带方案地问 |
| 反馈只记在脑子里、攒到轮末 | 漏掉、无法复用 | 即时登记，轮末归类（§1.2） |
| 只挖负面反馈 | 有效做法与优化方向白白流失 | 三类都挖，正向要放大（§1.2） |

## 10. 速查卡

**开工前**
1. 目的与验收清楚了吗（可测）？
2. 档位与时间盒定了吗？升档触发知道吗？
3. 写范围、依赖、主责、优先级定了吗？
4. 有没有更短路径？比较过两条吗？
5. 本轮会动到数据/接口/共享文件吗（→ 升档）？

**过程中**
1. 出现负面 / 正向 / 优化方向，记下来了吗（§1.2 即时登记）？
2. 动手前先策划了吗？不可逆的先写决策记录了吗（§1.4）？
3. 有阻塞预警信号了吗（§1.7）？

**交付前**
1. 对照验收标准逐条自查了吗？
2. 边界/异常/失败路径处理了吗？
3. 有无屎山、死代码、调试残留？
4. 证据齐了吗？回退路径有吗？
5. 用户最初的目的达到了吗？

**每轮结束**
1. 哪里最慢？哪里最痛？
2. 哪条规则该改（或为何不改）？
3. 有效经验固化到哪了？
