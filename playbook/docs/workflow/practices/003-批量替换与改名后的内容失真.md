## 批量替换 / 改名 / 结构重排后内容失真

- **症状**：脚本批量改完，`grep` 也确认"替换成功"，但读起来不对——引用指向不存在的文件、
  小节顺序颠倒、整段说明被覆盖丢失、术语被改成读不通的样子。Markdown 不会报错，只有人读才发现。
- **根因**：把"文本替换命中"当成"内容正确"。替换/改名/重排是**结构操作**，它破坏的是
  *引用关系与语义完整性*，而这两样都不在替换脚本的检查范围里。
  常见三个具体坑：
  1. **改名不改引用**——只改了定义处，所有引用处仍是旧名；
  2. **宽匹配误伤**——`## 5.` 匹配到了 `## 5.1`；整行替换把该行其它有用内容一起覆盖；
  3. **多轮脚本叠加**——上一轮的坐标/文本变成下一轮的输入，改一次错一次，且错误会累积放大。
- **解法**（改完必做，缺一步就是没改完）：
  1. **改前先列出全部受影响位置**（`grep` 出所有引用点，不只定义点）；
  2. 用**精确匹配**（带上下文、带边界），不用宽泛前缀；
  3. 改后跑**机械校验**：段落顺序、表格完整性、每处 `文件 §节` 引用能否解析、路径是否存在、
     术语是否全文一致（同一概念只允许一种写法）；
  4. **人工读一遍受影响的段落**——尤其被整段替换过的地方，机械校验查不出"读不通"；
  5. 多轮脚本修改时，每轮都重新读当前文件再改，不要沿用上一轮假设的坐标/文本。
- **验证**：把校验写成脚本固定下来，每次改文档都跑；对同一概念做全文一致性检查。
- **已固化到**：`08-反模式与速查.md` 反模式表（批量替换后只看 grep 结果）+ `09-环境适配与变更记录.md` 维护纪律
  （改完必须跑机械校验 + 人工复读）
- **首次/复发**：2026-11-26 至 11-28 间反复出现 4 次（引用改名未同步 ×2、宽匹配误伤与整段覆盖 ×1、
  术语替换失真 ×1）——**属高复发**，任何"用脚本改文档"的场景都会遇到。
